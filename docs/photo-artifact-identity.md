# Rendered photo identity and cache reuse

New worker-produced WebP URLs contain a SHA-256 identifier of the final encoded
bytes, after EXIF copying. The worker returns the full digest in each size's
`sha256` field. No database migration or client change is required: `sizes` is
already JSON, and clients consume the URLs in it.

```
opt/640_llm/<owner>/<photo>-<sha256>.webp
opt/640_llm/<owner>/<photo>-v7-<sha256>.webp
```

The worker's `/upload` and `/upload_async` endpoints accept an optional positive
32-bit integer `version` form field. Current clients do not send it and receive
hash-only names. Future clients may send their upload version; it becomes a
filename namespace and is recorded as `artifact_version` in size metadata.
There is no new JWT claim or client-side implementation in this change. For API
artifact uploads, a supplied version must match the database photo version.

`common/artifact_identity.py` centralizes the filename checksum length. We start
with all 256 SHA-256 bits. Readers accept byte-aligned 64–256-bit suffixes for a
future explicit shortening policy; the full checksum remains in DB metadata.
Analyzer reuse compares the full checksum and optional namespace, not merely
the shortened filename. Changing that policy later should include a collision
handling decision; a short filename is not a promise of collision-free storage.

## Pyramids and storage

A DZI descriptor alone identifies dimensions, not pixels. Shipped pyramids use
a deterministic digest covering the descriptor and every tile's relative name
and full SHA-256. The same tagged stem names both the descriptor and tile root:

```
opt/dzi/<owner>/<photo>-<digest>.dzi
opt/dzi/<owner>/<photo>-<digest>_files/<level>/<tile>.webp
```

API uploads remain bound to the authorized owner and photo. Legacy names remain
accepted. Local pool orphan accounting strips the new identity suffix to find
the owning photo, and continues checking actual DB references. Deletion follows
stored URLs, so old and new shapes are both supported. Existing public files
are not renamed, removed or regenerated by this change. Operator-owned external
pyramids served directly from an auxiliary worker's archive retain their existing
pass-through URLs; pyramids shipped into production pools receive the new identity.

## Analyzer behavior

The upload MD5 remains the grouping key for saved histories. For a selected image
that has a DB `sha256`, model reuse, model-coverage checks and disk distillation
require matching image evidence. New sessions record `image_content_sha256` and
the optional `artifact_version`. Older locally fetched `image_hash` values can
also establish matching bytes when the version namespace matches. Answers for
older renders remain on disk for reports and evaluation; they do not count as
answers for changed pixels. Unhashed legacy image records retain the previous
compatibility behavior, so transferring existing datasets does not trigger mass
reanalysis. Curated imports with insufficient image identity cannot override a
new hashed render. A concurrent photo/annotation change also prevents native
acquisition from publishing its stale result.

OpenRouter still receives the URL directly. The analyzer performs no new local
download or checksum calculation for this identity. The existing Claude Batch
preparation path, which fetches images for token counting/provenance, additionally
checks fetched bytes against the DB checksum when one is available.

## Deployment

Deploy API support before enabling the new worker: old APIs reject the tagged
artifact paths. Deploy the analyzer update alongside/before new worker outputs
so it does not reuse MD5-only histories for a new render. No client release is
required; the optional filename version can be adopted in a future one.

New URLs prevent stale content caches on subsequent processing, but do not purge
previously cached unversioned URLs or revoke already downloaded copies. Stricter
anonymization still needs a separate cache-retention/purge policy.
